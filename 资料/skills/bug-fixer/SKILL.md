# Bug Fixer - 精准 BUG 修复（自验→大佬验）

## 概述

修 BUG 的正确姿势：
1. 听描述 → 精准定位
2. 修复
3. **全量扫一遍**（不是只扫描述的地方）
4. **我自己先验证多遍**，确认没问题了
5. **再请大佬来验证**
6. 如果还有问题 → 再来一轮，最多 5 轮

这做个应用就一万个问题，修一个又一个，正常。所以多给几轮机会。

---

## 工作流总览

```
一轮完整的循环：

  听描述定位 → 修复 → 全量检测 → 自行验证(多遍) → 请大佬验证
                                                      │
                                          ┌───────────┘
                                          ▼
                                    还有问题？→ 再来一轮（最多5轮）
                                    通过了？→ 出报告，结束
```

**最多 5 轮循环**，5 轮还搞不定就出报告标注。

---

## 一轮循环的完整流程

下面的 Step 1~5 组成 **1 轮修复循环**。每轮都走一遍，最多走 5 轮。

---

### Step 1: 听描述，精准定位（Listen & Locate）

#### 目标
听用户的 BUG 描述，快速精准地定位问题。

#### 步骤

1. **认真听用户描述**——别打断，等他说完。

2. **主动追问必要信息**（如果描述不够明确）：
   - 哪个文件？哪个功能？
   - 报什么错？错误信息贴出来？
   - 什么操作触发的？
   - 有截图或日志吗？

3. **定位到文件+行号**：
   - 读取涉及的源代码文件
   - 理解代码逻辑和 BUG 根因
   - 确认确实是 BUG（排除用户误解）

4. **如果用户只说"有bug"没具体描述**，才做轻量扫描摸底：
   - 运行项目的基础检查（语法检查、lint）
   - 结合项目上下文推测最可能的 BUG
   - 列出可能的范围让用户确认

#### 产出
- 已知 BUG 位置（文件:行号）
- BUG 根因分析

---

### Step 2: 修复 BUG（Fix）

#### 原则
- **一次修一个 BUG**，逐个处理
- 每次修改后立即做语法检查，确保没引入新错误
- 优先最小化修改：只改有问题的行，不重构无关代码
- 如果一个 BUG 有多个修复方案，选最安全、破坏性最小的
- **不搞批量改**，改完一个确认一个

#### 修复策略

| BUG 类型 | 修复策略 |
|---------|---------|
| 语法错误 | 修正语法，补全缺失的括号/分号/引号 |
| 类型错误 | 修正类型标注或类型转换 |
| 未定义变量 | 补全 import 或修正变量名 |
| 逻辑错误 | 修正条件判断/循环/算法逻辑 |
| 空指针/None 检查 | 加 None 守卫 |
| 资源泄漏 | 补 finally/context manager |
| 导入错误 | 修复模块路径或安装缺失依赖 |
| 运行时错误 | 分析堆栈追踪，定位根因修复 |

#### 步骤

1. 读取目标源代码文件
2. 理解 BUG 根因
3. 应用修复（使用 Edit/Write 工具）
4. 立即做语法检查确认修改没问题
5. 记录修改了什么、为什么这么改

---

### Step 3: 全量检测——整个项目扫一遍（Full Scan）

#### ⚠️ 关键变化
**不是只扫用户描述的那一小块，而是整个项目全面扫描。**

#### 步骤

1. **运行项目对应的全量检测工具**：
   - Python: `python -m py_compile` + `pylint` / `mypy`（如果有）
   - Node.js/JS/TS: `tsc --noEmit` + `eslint`
   - Go: `go vet`
   - Rust: `cargo check` + `clippy`
   - 其他：根据项目类型选合适的工具

2. **运行全部已有单元测试**：
   - `pytest` / `jest` / `go test` / `cargo test` 等
   - 确保不引入回归

3. **确认结果**：
   - ✅ 全量检测通过（无错误/警告，测试全过）→ 进入 Step 4
   - ❌ 还有 BUG → 全部记下来，回到 Step 2 逐一修复

---

### Step 4: 自行验证——我来验，确认没问题（Self-Verification）

#### ⚠️ 关键
**这一步是我自己验证，不打扰大佬。** 验证多遍，确认真的没有问题了，才到下一步请大佬验。

#### 步骤

1. **针对 BUG 场景做运行时验证**：
   - 如果是脚本：直接运行，复现触发条件
   - 如果是应用：启动应用（短暂运行 5-10 秒），检查无崩溃
   - 如果是 API：发请求测试相关接口
   - 如果是 UI 逻辑：检查相关逻辑路径

2. **验证多遍**（不只是一次就跑）：
   - 同一个 BUG 场景至少验证 **2~3 次**，确认稳定
   - 检查相关的上下游逻辑是否被影响
   - 如果有测试，运行相关测试确保通过

3. **自我判断**：
   - ✅ **确认没问题了** → 进入 Step 5，请大佬验证
   - ❌ 还有问题 → 回到 Step 2 重新修复

#### 重要
- **在确认没问题之前，不要打扰大佬**
- 多验几遍，确保自己确定修好了
- 宁可多花时间自验，也不要让大佬验出问题

---

### Step 5: 请大佬验证（User Verification）

#### ⚠️ 关键
**前面 Step 3 全量检测通过 + Step 4 自行验证确认没问题 → 才到这一步。**

#### 步骤

1. **向大佬报告修复结果**：
   - 描述修了什么 BUG
   - 出示检测结果（全量扫描通过、测试通过）
   - 出示自验结果（运行时验证通过）
   - 说明：「我已确认没问题，麻烦大佬看看还有没有遗漏？」

2. **等待大佬亲自验证**：
   - 大佬说 OK → **本轮通过，进入最终报告**
   - 大佬发现问题 → 记录新问题，**进入下一轮循环**

---

## 循环控制

### 最多 5 轮

每轮循环走完 Step 1~5，记作 **1 轮**。

| 轮次 | 说明 |
|------|------|
| 第 1 轮 | 首次修复 + 全量检测 + 自验 + 大佬验 |
| 第 2 轮 | 大佬验出问题？再来一轮 |
| 第 3 轮 | 同上 |
| 第 4 轮 | 同上 |
| 第 5 轮 | **最后一轮**，搞完不管什么结果都收工 |

**5 轮结束后**：
- 如果还有问题 → 出报告标注「5 轮未完全修复，建议人工介入」
- **绝对不进行第 6 轮**

---

## 最终报告

每轮结束后输出简洁报告，第 5 轮出最终汇总：

```
╔══════════════════════════════╗
║   BUG 修复报告 (第X轮)       ║
╠══════════════════════════════╣
║ BUG 位置:    file.ts:42       ║
║ BUG 描述:    [描述]            ║
║ 修复方案:    [做了什么]         ║
║ 全量检测:    ✅ 无 BUG         ║
║ 测试套件:    ✅ X/X passed     ║
║ 自行验证:    ✅ 确认没问题      ║
║ 大佬验证:    ✅/❌             ║
║ 当前轮次:    X / 5            ║
║ 最终状态:    ✅ / ⚠️ 未完全修复 ║
╚══════════════════════════════╝
```
