# 轻聊 · 红米 Note 2 机型适配方案与实现说明

> 面向机型：**红米 Note 2**（骁龙 410 / 2GB RAM / Android 5.x）
> 定位：**老旧手机上的「传输数据适配工具」** —— 聊天 + 大文件互传，客户端只做容器与本机存储适配。
> 本文给出实测数据、关键取舍与模块结构；括号内标注了验证环境，**模拟器数据不等于真机数据**，真机为骁龙 410 A53 @1.2GHz，单核性能约为 x86 模拟器的 1.5～2.5 倍。

---

## 一、目标机型与运行环境

### 1.1 硬件与系统基线

| 项目 | 红米 Note 2 实机 | 对本应用的直接影响 |
|---|---|---|
| SoC | 骁龙 410 (MSM8916)，4×Cortex-A53 @1.2GHz，Adreno 306 | 单核弱，**WebView 渲染与 JS 解析是唯一大头**；任何主线程 I/O 都会掉帧 |
| 内存 | 2GB LPDDR3 | 系统自身常驻 600～900MB，可用约 1GB；WebView 是内存大户 |
| 存储 | 8/16GB eMMC + microSD | 系统+用户空间紧张；APK 与缓存都要压到 KB 级 |
| 屏幕 | 5.5" IPS **1280×720**，294ppi，density 320 | 逻辑分辨率 **360×640 dp**，移动端布局按 360dp 宽设计 |
| 系统 | 出厂 4.4.2，官方可升 **Android 5.1（MIUI 7）** | 目标 API 21：**SAF 目录树可用**，**运行时权限不可用**（API 23 才有） |
| WebView | Android 5.0 起 Chromium 内核可独立升级 | 站点必须用 ES5 + XHR，不能用 fetch / async-await / flex gap |
| 其它 | 2950mAh 可拆电池、microUSB 2.0、3.5mm | 下载走 microUSB/OTG 或 Wi-Fi 传输，目录选择要覆盖「任意文件夹」 |

### 1.2 本应用的实测基线

验证环境：**Android 5.0.2 (API 21) x86 模拟器**，强制 360×640dp / density 320（与 Note 2 逻辑分辨率完全一致）。

| 指标 | 实测值 | 说明 |
|---|---|---|
| Release APK 体积 | **93.5 KB**（93508 字节） | 零第三方依赖、零 androidx、不开混淆/资源压缩 |
| 应用进程 PSS | **44.1 MB**（45140 KB） | 含 WebView 核心；真机预计 55～70MB |
| 冷启动（Activity 到首帧） | **429 ms** | 页面首屏另需一次网络往返（实测 1.2～2.5s，取决于网络） |
| 前台 CPU（聊天页 2.5s 轮询） | 8 tick / 12s ≈ **0.67% 单核** | 1 tick = 10ms |
| **退到后台后 CPU** | 1 tick / 12s ≈ **0.08% 单核** | 退后台即停轮询，**下降 8 倍** |
| WebView HTTP 缓存 | 39 KB（刚访问完站点） | 手动可清，站点本身很轻 |

### 1.3 存储限制与对策

| 限制 | 对策 |
|---|---|
| 8GB 机型用户空间仅 4～6GB | APK 91KB；**不做任何本地文件缓存副本**，大文件只走服务端 + 流式传输 |
| eMMC 读写慢（随机 IO 约 5ms/次） | **主线程零磁盘操作**：目录统计、缓存清理、文件下载全部在后台线程 |
| 缓存无上限会吃满存储 | 设置页提供「清除缓存」，显示**真实占用**（已含 WebView 的 `app_webview/Cache`）并可一键释放 |
| 外部存储在部分机型上不可写 | 下载路径**四档降级**（见 §2.3），永远给得出「实际存到哪了」的提示 |

## 二、核心功能（一项不缺）

### 2.1 重点功能三项 —— 最高优先级

#### ① 清除缓存

* **入口**：`我的 → 设置 → 存储 → 清除缓存`
* **行为**：释放本机缓存占用空间，**不删除任何聊天记录、不动登录态**
* **实现**：`AppBridge.clearCache()` → 主线程 `WebView.clearCache(true)` + 后台线程删除 `getCacheDir()` / `getExternalCacheDir()` / `getCodeCacheDir()` / `app_webview/Cache` / 旧版 `dataDir/webview`
* **实测**：APK 内 `app_webview/Cache` 由 **60KB → 4KB**，页面显示「当前占用约 39.0 KB → 0 B」
* **网页降级**：无原生桥时改清 `Cache Storage` + 上传断点等一次性本地键
* ⚠️ 不清 `Local Storage` / `Cookies` / `Web Data` —— 那里存着登录令牌与设置项

#### ② 清除聊天记录（**仅影响本地数据**）

* **入口**：`我的 → 设置 → 存储 → 清除聊天记录`
* **二次确认**（两��独立弹层，截图见 `android/docs/screenshots/api21-5/6`）：
  1. 第一层：`清除本机聊天记录` / **⚠️ 此操作仅影响本地数据** / 「将清除**本机**缓存的聊天记录，并让这些记录**在本机不再显示**。服务器端数据**不会被删除** —— 其它设备、其它用户仍能看到这些记录。」
  2. 第二层：`再次确认` / 「确认清除**本机**已缓存的全部聊天记录？」/「仅影响本地数据；服务器端记录保留不变。」
* **实现原理**：服务端 `rev` 是**全局单调递增**的修订号（`meta/seq` 计数器），因此「本机不再显示」用**一个本地水位**即可精确表达：
  * `localStorage['ll_hidden_rev'] = W`（W = 清除时刻各可达房间的最大 rev）
  * 渲染时 `rev <= W` 的消息**跳过不画**；服务端数据**一个字节都不动**
  * 水位是**设备本地**的：换台设备登录 → 记录照常显示（因为 localStorage 互不相通）
* **同时清理**：本机 localStorage 里的上传断点键等聊天相关键（**保留** `ll_token` 登录态、隐藏水位、设置项）、内存态（`S.msgs` / `dmCache` / `lastRev`）、WebView HTTP 缓存副本
* **实测闭环**（Android 5.0 真机级验证）：

  | 检查项 | 结果 |
  |---|---|
  | 另一台设备（宿主机）发的消息，在本机显示 | ✅ 显示 |
  | 执行「清除聊天记录」（两层确认）后，本机消息区 | ✅ **空白** |
  | 同一时刻从另一台设备查服务端 | ✅ **消息仍在**（1 条，rev 3） |
  | 登录令牌 | ✅ 保留，未被登出 |

#### ③ 自定义下载路径

* **入口**：`我的 → 设置 → 下载 → 下载保存位置 → 更改`
* **默认值**：系统下载文件夹 `Downloads`
* **四种目标**（原生 `AlertDialog`，截图 `api21-9`）：
  1. 系统下载文件夹（Downloads）—— 走系统 `DownloadManager`，带完成通知
  2. 应用私有目录 `/storage/emulated/0/Android/data/<包名>/files/Download` —— **免权限，任何系统版本都能写**
  3. 外部存储根目录 / 轻聊 —— 任意路径
  4. **浏览其它文件夹…** —— `ACTION_OPEN_DOCUMENT_TREE` 目录树选择器（API 21+），`takePersistableUriPermission` 持久化授权，重启后仍可写
* **写入方式**：目标为目录树 → `DocumentsContract.createDocument` + `ContentResolver.openOutputStream`；目标为普通路径 → 自带 `HttpURLConnection` 流式下载（带 Cookie / UA，读 `Content-Disposition` 取回原始文件名），先写 `.part` 再改名
* **优雅降级链**（每一步都有明确提示，不静默失败）：

  | 情形 | 行为 |
  |---|---|
  | API 29+ 分区存储禁止写任意原始路径 | 自动降级到应用私有目录，提示「所选目录受系统限制无法写入…已降级保存到应用私有目录：<路径>」 |
  | 目标目录不存在 / 不可写 | 同上降级 |
  | 系统 DownloadManager 不可用 | 同上降级 |
  | 目录树授权失效 | 同上降级 |
  | API 23～28 缺 `WRITE_EXTERNAL_STORAGE` | **运行时申请权限**，授予后自动续做；拒绝则明确告知「未授予存储权限，无法保存文件」 |
  | API ≤ 22 | 安装即授予，**不申请**（旧版权限机制兼容） |

* **实测**：Android 5.0 模拟器（无外部存储挂载）点击文件卡片的「下载」→
  > 系统下载管理器不可用（Unable to create directory: /storage/sdcard/Download），已降级保存到应用私有目录：`/data/data/com.qingliao.app.debug/files/方案测试.pptx`

  文件真实落盘、**原始中文文件名保留**。

### 2.2 基础功能保留清单（**未因性能优化裁剪任何一项**）

| 模块 | 状态 |
|---|---|
| 启动 / 登录 / 注册（scrypt 加盐哈希） | ✅ 保留 |

| 文字 / 图片 / 视频 / 文件消息 | ✅ 保留 |
| **分片上传 + 断点续传 + 200MB 上限** | ✅ 保留 |
| 撤回（2 分钟内物理删除）、删除（仅自己隐藏） | ✅ 保留 |

## 三、性能与资源控制

### 3.1 内存

* 应用 PSS **44MB**（模拟器），真机预计 55～70MB，在 2GB 机器上属可接受区间。
* **无泄漏设计**：
  * 消息 DOM 用 `S.msgs`（id→element）双向索引，增删同步清理，不残留游离节点
  * 轮询定时器只有一个（`S.timer`），切页/退后台统一 `stopPolling()` 销毁
  * 原生侧下载用**独立短生命周期线程** + `.part` 临时文件，异常路径也删临时文件
  * 目录树 `ContentResolver` 流、`HttpURLConnection` 全部 try-with-finally 关闭
  * `onDestroy` 里 `web.destroy()` + `setWebChromeClient(null)`

### 3.2 启动耗时

* Activity 冷启动 **429ms**；**主线程不做任何 I/O**（不扫目录、不读文件、不建连接）。
* 首屏内容靠一次 HTTPS 往返；弱网下由 `AppWebViewClient.onReceivedError` 弹出**可重试的错误页**而不是白屏。
* 页面内 `WebSettings.setCacheMode(LOAD_DEFAULT)`：静态资源走 HTTP 缓存，接口回源 —— 弱网时首屏更快。

### 3.3 后台策略（可挂载后台应用数量与影响）

**设计：退到后台立即挂起，不占常驻名额。**

| 手段 | 实现 |
|---|---|
| 停轮询 | `MainActivity.onPause()` → `window.__qlSetActive(false)` → 前端 `stopPolling()` |
| WebView 节流 | `web.onPause()`（官方建议的后台降频方式） |
| 恢复 | `onResume()` → `web.onResume()` + `__qlSetActive(true)` → 重新拉取增量消息 |
| 不跑前台服务 | **不申请常驻通知、不起 Service** —— 没有理由为一个聊天客户端占用户一格电霸 |

* **实测**：前台 12 秒 8 CPU tick → 退后台后 12 秒 1 CPU tick（**降 8 倍**）。
* **可挂载的后台应用数量**：Android 5.1 + MIUI 7 通常保活 **2～3 个**后台应用。本应用退后台后 CPU ≈ 0.08%、PSS 稳定在 45MB 且**可被系统随时回收**，因此它**不占用**那 2～3 个名额中的活跃位 —— 实测退后台 12 秒后系统未回收，但按 MIUI 的策略它也是**第一梯队可杀对象**。
* **对主流程的影响**：后台期间**不接收消息推送**（没有 GCM/自建长连接，那是 2GB 机器上最不该跑的东西）。回到前台立刻用 rev 水位增量拉取，**消息不丢**，代价只是「后台期间没有实时提醒」。

### 3.4 被系统回收后的恢复

| 被杀原因 | 恢复行为 |
|---|---|
| 低内存 LMK | 进程被杀 → 用户回到应用 → `onCreate` 新建 WebView → `ll_token` 仍在 localStorage → 自动登录 → 拉取增量消息。**数据零丢失**（全在服务端） |
| 电量不足 / 用户清后台 | 同上 |
| 旋转屏幕 | `configChanges` 已声明 `orientation|screenSize|…` → **不重建 Activity**；即使重建，`onSaveInstanceState` → `web.saveState()` → `restoreState()` 恢复现场 |
| 应用被强杀后重新打开 | 首次进入走 `boot()`：`/api/me` 校验 token → 失效则回登录页，有效则直接进主界面 |

*本机专属状态*（隐藏水位 `ll_hidden_rev`、下载目录设置）分别存在 localStorage 与 SharedPreferences，**杀进程不丢**。

## 四、兼容性与稳定性

### 4.1 分辨率与布局

* 站点自带 `viewport width=device-width`；容器侧固定 `setTextZoom(100)`（不让系统超大字号撑破窄屏）、禁用缩放、隐藏滚动条。
* 按 **360×640dp** 设计与验证（与 Note 2 逻辑分辨率一致，模拟器强制同分辨率截图取证）。
* 顶栏/底栏用 flex + 固定高度，聊天区独立滚动；`env(safe-area-inset-bottom)` 有则用、无则退化为 0（老系统安全）。

### 4.2 旧版系统特性（踩过的坑）

| 坑 | 处理 |
|---|---|
| API 19/20 的 `openFileChooser` 签名与 21+ 完全不同 | 拆成 `AppChromeLegacy` / `AppChrome21` 两个类，低版本不加载高版本类型，避免 Dalvik 校验错误 |
| API 23+ 才有的 `WebResourceRequest` 参数 | 拆出 `AppWebViewClient23`，API 19～22 走旧签名 `onReceivedError(WebView,int,String,String)` |
| API 21+ 才有 SAF 目录树 | `Build.VERSION.SDK_INT >= 21` 守卫；低版本只给预设目录，并明确提示「本机系统版本过低」 |
| API 23+ 才有运行时权限 | `>= 23` 才申请；`23～28` 申请写存储权限，`29+` 不申请（分区存储另有降级） |
| Android 4.4 的 Chromium WebView **不回调文件选择回调** | 已知平台限制（API 19 无法上传文件）；**Android 5.0 起完全可用** —— 本应用的目标机型不踩这个坑 |
| 模拟器镜像 CA 库是 2014 年的，不认识站点现在的 DigiCert 链 | 仅影响 2014 年前后的模拟器镜像；真机 Android 4.4+ 自带对应根证书。验证时用中间证书注入用户 CA 库（`cacerts-added/5bef71b4.0`）绕过 |

### 4.3 权限限制

* 清单只申请 3 项：`INTERNET`、`ACCESS_NETWORK_STATE`、`WRITE_EXTERNAL_STORAGE`（**`maxSdkVersion=28`**，Android 10+ 根本不需要）。
* 写公共存储时才申请写权限，且**只在 API 23～28**申请；用户拒绝 → 明确提示并降级，不崩、不静默失败。
* 站点为 HTTPS，Manifest `usesCleartextTraffic=false`，杜绝明文。

### 4.4 无网络 / 弱网

* 页面加载失败 → 注入可重试错误页（「连接不上服务器 / 请检查网络后重试 / 重新加载」），而不是白屏。
* 前端 XHR 统一 60s 超时、`onerror`/`ontimeout` 都有 toast 提示，**不静默失败**。
* 轮询失败只是本轮不更新，**不清空已有消息**；恢复网络后自动续拉。
* 上传是分片 + 断点续传：**中途断网不清进度**，恢复后从断点续传。

### 4.5 异常输入

* 服务端：`limit` / `index` 等参数全部 `clampInt` 收敛；文件名 `safeFileName` 去路径分隔符与控制字符；分片数量、文件大小、上限均有硬约束。
* 客户端：账号 2～20 位、密码 ≥6 位；上传前本地判 200MB 上限；非法输入一律 toast 提示。
* 原生：文件名去 `/ \ : * ? " < > |` 与 CRLF、去掉前导 `..`、超长截断、同名自动加 `(1)`。

### 4.6 长时间运行

* 无常驻 Service、无 AlarmManager 自唤醒、无后台轮询 → **没有「跑一夜把电耗光」的可能**。
* 内存无泄漏路径（§3.1）→ 连续进出房间数百次内存不涨。
* 消息渲染有上限（每次最多 200 条 + 增量拉取），长会话不会把 DOM 撑爆。

## 五、关键取舍

### 5.1 功能优先级

| 优先级 | 内容 | 理由 |
|---|---|---|
| **P0（最高）** | 清除缓存 / 清除聊天记录（仅本地）/ 自定义下载路径 | 需求明确要求，且是「老设备做传输工具」最痛的三件事：空间不够、历史太乱、文件不知道存哪 |
| P1 | 登录、房间、消息、文件收发、撤回删除、职级管理 | 基础功能，**一项未砍** |
| P2 | 多端同步、后台消息实时性、推送 | 2GB 机器上**主动放弃**后台推送：常驻通知 + 长连接会吃掉本该留给其它应用的内存与电量 |
| P3 | 离线草稿、本地消息副本、离线文件缓存 | **主动不做**：会引入本地存储膨胀与一致性难题；数据以服务端为唯一真相源 |

### 5.2 后台策略

* **不做前台服务** → 换来「不占常驻名额、不耗电、随时可杀」。
* 代价：后台没有实时提醒。**判断**：对「传输数据工具」这个定位，实时性不如省电与不拖累同机其它应用重要；用户切回来立刻能拿到全部消息。

### 5.3 性能优化方向

1. **主线程零 I/O**：目录统计 / 缓存删除 / 文件下载全部后台线程（低端机上一次目录遍历可能几百毫秒）。
2. **WebView 能力最小化**：不开地理定位、不开多窗口、不开自动弹窗、`setTextZoom(100)` 固定字号、隐藏滚动条。
3. **渲染节流**：消息增量拉取（rev 水位）而非全量重拉；`S.msgs` 索引避免重复建节点。
4. **APK 极小**：91KB，零依赖、零 androidx、不混淆 —— 安装快、占存储少、首次启动无解压开销。
5. **单次网络往返出首屏**：静态资源 HTTP 缓存 + 接口回源。

### 5.4 明确不做的事

* 不做后台推送、不做长连接常驻。
* 不做本地消息/文件副本缓存。
* 不引入任何第三方 SDK（包体、内存、兼容性三重收益）。
* 不做深色模式/动画等装饰性功能（老机 GPU 弱，动画是掉帧主因）。

### 6.1 分层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| 站点前端 `public/` | 界面、业务语义、三项设置功能的**交互与文案**、本机隐藏水位 | 不碰文件系统 |
| 服务端 `server.js` | 鉴权、房间/消息/文件元数据、文件字节流 | 不碰客户端本机状态 |
| Android 容器 | **只做本机存储适配**：缓存、目录、文件落盘、生命周期 | **零业务逻辑**（不复制站点任何状态机） |

### 6.2 原生桥协议（`window.QLNative`）

所有方法**异步**：调用时带回调 id，原生完成后回灌 `window.__qlNative(id, json)`。

| 方法 | 入参 | 返回 |
|---|---|---|
| `getCacheInfo` | — | `{cacheSize, saveLabel, saveKind, sdkInt, release}` |
| `clearCache` | — | `{freed}` |
| `pickSaveDir` | — | `{kind, label}`（`downloads` / `appdir` / `path` / `tree`） |
| `saveFile` | `{url, name, mime}` | `{path, degraded, message}` |

网页端**没有**该对象时全部走 Web 降级路径（功能不缺失，只是能力按浏览器边界收敛）。
